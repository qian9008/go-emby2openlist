## pelagica 子模块合并（同日，策略不同）

### 关键判断：子模块不能用 squash
- dev 领先 main **211 个提交**，但其中仅 11 个是自有提交（qian9008）
- 其余 200 个为上游官方作者：KartoffelChips 82、Jan Straßburger 57、Mihai 14、dependabot 12 等
- 仓库配置了 `upstream = PelagicaApp/pelagica`，dev 上存在 `backup/dev-before-sync-*` 分支，说明持续跟上游同步
- **若 squash 上游提交 → git 失去共同祖先 → 下次 merge upstream/develop 会把已有代码当新变更重放，产生海量冲突**

### 实际采用
- `git switch main && git merge --no-ff dev -F msg` → 合并提交 `68804d67`
- 211 个提交全部进入 main，作者归属与上游追踪关系完好
- `git rev-list --count main..upstream/develop` = 0，说明当前已完全跟上 upstream/develop
- 主仓库同步更新子模块指针：`cb4486e`

### 经验结论
- 全是自己的脏提交 → squash 合理（主仓库场景）
- 含第三方/上游提交的 fork 仓库 → 只能用 `--no-ff` merge，禁止 squash
- **修正**：子模块 `origin` 远端**存在** dev 分支，且与本地 dev 同为 `abec7ad6`。
  之前误判为「远端无 dev」，原因是该仓库 `remote.origin.fetch` 被限制为
  `+refs/heads/main:refs/remotes/origin/main`，`git branch -r` 看不到 dev，
  `git rev-parse origin/dev` 直接报 "Needed a single revision"。
  **判断远端分支必须用 `git ls-remote --heads origin`，不能依赖本地 remote-tracking。**

### 远端 main 的异常状态（需留意）
- 远端 `qian9008/pelagica` 的 main 实际指向 `d551aa48`（tag 4.11.1，上游官方合并提交），
  **不是**本地旧的二开 main `5e6a2f4d`，两者互不为祖先，说明远端 main 曾被 force push 覆盖成上游版本
- 但 `main..origin/main` = 0，即 d551aa48 已被 dev 链（经上游同步）包含，
  因此 `git push origin main` 仍是**快进**：`d551aa48..68804d67`，无需 force
- 本地 `refs/remotes/origin/main` 曾长期停留在 5e6a2f4d，与远端不符，fetch 时会报
  `! [rejected] main -> origin/main (non-fast-forward)`，属正常现象（方向相反）
- 子模块 `webos/` 已被跟踪（18 个文件），`node_modules` 未入库，正常

## pelagica 历史重组：26 条二开提交 → 4 条（方案 A）

### 决策依据
- `git log upstream/develop..main` = 26 条，作者全是 qian/qian9008（同一人两个 git 身份）
- 上游 1264 个提交（含 4.14.0）全在 `upstream/develop`（`075b5b20`）及更早，是 main 的祖先
- **只压 10 月不可行**：10/22 的 merge `bbae35bb` 正是上游 4.14.0 进入 main 的通道，
  它的上游父提交不在 9/20 那条线的祖先链上，按日期切分会把上游提交吞进二开提交
- 「跨 merge 选择性 squash」需 `rebase -i --rebase-merges` 重放两个上游大 merge，冲突成本高

### 执行步骤
1. `git tag backup/main-before-reorg-20261029`（旧树 `93312ee9`）
2. `git reset --mixed upstream/develop`（工作区不动，差异全部转为未暂存）
3. 按路径分 4 批 `git add -A` + commit：
   - `chore(build)`：.gitignore、config.schema.json、dev.sh、Dockerfile、pnpm-lock.yaml、pnpm-workspace.yaml
   - `feat(backend)`：backend/collector/
   - `feat(frontend)`：frontend/、packages/
   - `docs`：根级 5 个 .md
4. `git branch -f dev main`
5. `git push --force-with-lease origin main`、`--force-with-lease=dev:<旧hash> origin dev`

### 校验结果
- 新旧树哈希**完全相同**：`93312ee99279faaf0332751028a681121e087843` → 内容零丢失
- 上游历史 1264 条完整保留，`upstream/develop..main` = 4 条
- 远端 main/dev 均为 `57111213`，与本地一致

### 踩坑
- `--force-with-lease` 对 dev 报 `stale info`：手动用 refspec fetch 建立的 `origin/dev`
  缺少 tracking 元数据。解决方式 → `--force-with-lease=dev:<期望hash>` 显式指定，绕开元数据。
- 空结果命令 `git status --short | wc -l` 输出 0 但 exit code 1，串联命令时注意用 `|| true`。
