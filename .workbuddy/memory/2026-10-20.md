## ffmpeg 抽帧 0 字节根因与修复

- 现象：`[thumb-debug] ffmpeg 抽帧失败 ... size=0`，ffmpeg 能"打开"输入但抽不出帧。
- 用户指出真因：`.strm` 文件只是指针，内容即真实下载地址（`http://host/d/<path>?sign=`），
  而旧实现 `getRealDownloadUrl(t)` 用 `t.Path`+`t.Sign` 重新拼 `sw.OpenlistPath`，
  合并上游 v2.9.0 后改为重建直链，可能因当前列表 sign/path 与写入时不匹配导致 URL 失效 → 抽到 0 字节。
- 修复方向（用户明确）：抽帧应「打开本地 xx.strm → 读出里面已验证可播的真实 URL → 喂给 ffmpeg」。
- 改动：
  - `task.go`：`getRealDownloadUrl(openlistUrl string)` 改为接收 URL 字符串（不再接 FileTask）；
    VirtualWriter/MusicWriter 调用改为 `getRealDownloadUrl(sw.OpenlistPath(task))`。
  - `synchronizer.go`：新增 `resolveFFmpegInput(task, localAbsPath)`，
    对 `.strm` 文件优先 `os.ReadFile` 读内容作为抽帧输入（src="strm"），读不到再退回 `getRealDownloadUrl(sw.OpenlistPath(...))`；
    ffmpeg 分支改为 `dlUrl, src := resolveFFmpegInput(...)` 并打印 `src` 便于排查。
- 验证：`go build ./...` 与 `go vet` 通过。
- 待办：诊断日志 `[thumb-debug]` 仍保留，等用户真机验证 ffmpeg 出图后删除；未提交（待用户确认后提交推送）。

## ffmpeg size=0 第二层根因：代理误代理局域网地址

- 新二进制已生效（日志出现 `src=strm url=http://192.168.50.99:5244/d/...`，且 strm URL 无 `?sign=`，说明写入时 sign 为空但播放器可用）。
- 仍 `size=0`：根因是 `ffmpeg.getProxyUrlByPath` 对所有 http URL 返回 http 代理地址，
  ffmpeg 把"访问局域网 openlist(192.168.50.99:5244)"的请求也走了外网代理 → 代理连不到 LAN → 空响应 → size=0、无 Error opening input。
  播放器(Emby/Jellyfin)不走该代理所以能播。
- 修复：`getProxyUrlByPath` 增加私网/本机/链路本地 IP 跳过代理（标准 NO_PROXY 行为）。
  局域网 openlist 直连，其 302 到外网上游时外网地址仍正常走代理。
  该改动同时惠及其他用 ffmpeg 拉取 openlist 直链的地方（VirtualWriter/MusicWriter）。
- 验证：`go build ./...` 与 `go vet` 通过。
- 仍需用户重新编译重启验证 ffmpeg 是否出图。

## 修正：代理是否真因需先确认 + ffmpeg 吞错修复

- 用户质疑：「所有资源都在内网，代理应该没问题」——合理。需先确认前提。
- 关键事实：`webproxy.HttpUrl/HttpsUrl` **不是从 config yaml 读取，而是从环境变量 `HTTP_PROXY`/`HTTPS_PROXY` 读取**（webproxy.go init）。默认 nil（不启用）。
  即：只有运行 8095 的 shell 里设了这两个环境变量，ffmpeg 代理才会参与。若没设，代理根本不是因素，此前"代理导致 size=0"的推断不成立，需找别因。
- 更关键的根子：`ExtractVideoCover`/`ExtractMusicCover` 只要 ffmpeg stderr **不含** `Error opening input` 这个确切串，
  就**静默吞掉错误**返回 `(空字节, nil)`。这解释了日志 `err=空 size=0`——真实失败原因（代理连不上/非视频/seek 越界）被藏起来了。
- 修复（优先于猜代理）：让 ffmpeg 失败时返回**真实 stderr**（fmt.Errorf 含 stderr 文本），不再吞错。
  `synchronizer.go` 抽帧失败日志拆为两行：`err!=nil`（带真实 stderr）与 `len(pic)==0`（seek 越界/非视频提示），并补上 `url=` 便于对照。
- 当前状态：代理修复（私网 NO_PROXY）仍保留，属防御性——仅在 `HTTP_PROXY` 设了且代理不回环内网时必要；
  若用户没设 `HTTP_PROXY`，则该修复为 no-op，真实原因将由新 stderr 暴露。
- 待办：请用户确认运行环境是否设 `HTTP_PROXY`；重新编译后看失败日志的真实 stderr 定位；确认出图后删 `[thumb-debug]` 并 commit+push。

## 真正根因（一锤定音）：ffmpeg 二进制无执行权限

- 用户贴出新日志（带 url + 真实 err）：
  `err=ffmpeg 抽帧执行异常: fork/exec /config/lib/ffmpeg/ffmpeg_linux_amd64: permission denied`
- **真相**：ffmpeg 二进制文件缺少 `+x` 执行位，根本无法运行。这解释了之前所有 `size=0`——
  此前 `ExtractVideoCover` 把 "permission denied" 这类非 `Error opening input` 的错误静默吞成 `(空, nil)`，
  故日志显示 `err=空 size=0`。用户质疑"代理/虚拟地址不是原因"完全正确。
- 代码 bug：`auto_download.go` 的 `AutoDownloadExec` 在文件已存在分支只 `os.Stat` 检查"是否存在"，
  `execOk=true` 前**从不检查执行权限**，导致挂载卷中无 `+x` 的二进制被误判为可用，运行时才崩。
- 修复：新增 `ensureExecutable(path)`，检查 owner 可执行位（Perm()&0o100），缺失则 `os.Chmod(path, 0o755)`；
  两处生效——(1) 已存在分支先 `ensureExecutable` 再 `execOk=true`；(2) 下载完成后显式 `os.Chmod 0755`。
  chmod 失败（如只读挂载）返回明确错误提示用户手动 `chmod +x`，不再静默失败。
- 效果：Docker RW 挂载下重启自动修复权限；只读挂载下启动即报错指引手动 chmod，避免再次陷入 size=0 黑盒。
- 验证：`go build ./...` 与 `go vet` 通过。
- 关键旁证：先前"吞错修复"（让 ffmpeg 真实 stderr 暴露）是定位此根因的功臣，必须保留。
