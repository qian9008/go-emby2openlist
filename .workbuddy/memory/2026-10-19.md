## Jellyfin 12 鉴权兼容性修复（系统性 bug）

**现象**：用户测 `GET /api/share/users` 返回 `身份验证失败`（401）。经排查：
- 后端是 **Jellyfin v12.2.0**（非 10.9），且躲在反代后（容器真实地址 192.168.50.99:8096，对外 :8092）。
- **根因**：Jellyfin 12 默认禁用旧版鉴权（`?api_key=` 小写、`X-Emby-Token` 头、`/emby/` 前缀），只认 `Authorization: MediaBrowser Token="..."` 与 `?ApiKey=`（大写 K）。
- ge2o 所有回源调用都用旧方式 → 分享/播放/下载/代理全 401。

**修复**：新增 `internal/util/https/` 工具 `EmbyAuthHeaderValue` / `ExtractEmbyToken` / `(*RequestHolder).EmbyAuth`（避免 share↔emby 循环依赖）。
- 策略：**保留旧方式、补充 MediaBrowser 头**，Emby 不回归。
- `emby.go` 的 `ProxyOrigin` 转发前注入 MediaBrowser 头（含分享提权后的 adminKey），覆盖全部代理流量。
- 同步修复服务端直连：share.go(3处)、playbackinfo.go、media.go、playing.go、auth.go、api.go(RawFetch 集中处理)。
- 未处理 m3u8/proxy.go:125 与 365_thumb.go:64（目标 host 不确定，防令牌外泄），待真机验证。

**验证**：
- `go build ./...`、`go vet`、`go test ./internal/service/share/...` 全绿。
- 真机写临时测试（`zz_live_test.go`，事后删除）对 192.168.50.99:8092 验证：无注入 401、注入 MediaBrowser 后 200，复现并证明修复有效。
- 注意：Jellyfin 12 的 `/Users/Me` 用 **API Key** 调会 400（仅用户登录令牌可用）；production 调用方传的是用户令牌，不受影响。

## 缩略图生成在合并后失效的根因与修复（已修正根因）
**现象**：用户报 `exclude-365-paths` / `local-tree-gen.enable: true` / `ffmpeg-enable: true` 配置"没用了，不能生成缩略图"，且 `365-enable` 一直为 `true`。

**真因（二次排查后确认，之前误判为门控）**：上游 v2.9.0 把整个缩略图子系统重写为「365 插件 + ffmpeg」方案，**在 `synchronizer.go` 同一位置（写文件后）把 ge2o 原版 `DownloadThumb(task.Thumb)` 内联下载整段删除**，换成 `Enable365` + `FetchFsGet` 触发插件。合并时该区域为冲突区（ge2o 与上游都改过），**Agent 用 `git merge-file` 手动解冲突时采用了上游写法、删掉了 ge2o 原版内联下载**——这是 Agent 的手动决策，不是工具 bug；诱因是用户在合并前说过"OpenList 拉图可能和 365 插件重复，应该可以删除"。原 ge2o 主链路被删后，非排除路径改成只调 `FetchFsGet` 触发 365 插件钩子（`365_thumb.go`）。
- 365 插件仅在 `res.Thumb != ""` 时下载，而 `res.Thumb` 来自 `/api/fs/get` 的返回。
- 很多 openlist 版本在 `/api/fs/list` 返回 `thumb`、但 `/api/fs/get` 不返回 → 365 插件整段 no-op → **非排除路径（库的主体）完全无图**。
- `task.Thumb` 来自 `walkDir2SyncTasks` 的列表项（`FsGetTask` 取 `info.Thumb`），本就是最可靠、零额外请求的来源。
- 验证：`DirName="openlist-local-tree"`，`s.baseDir=BasePath/openlist-local-tree`，与 365 插件 `download365Thumb` 存图目录一致，故图存了能被读到。

**修复**（`synchronizer.go` 缩略图块，BUILD/VET 通过，**未提交**）：
1. 恢复「列表 Thumb 内联下载」为主链路：`if !isExcluded && task.Thumb != "" { go openlist.Download365Thumb(task.Path, task.Thumb, filepath.Base(task.Path)) }`（复刻原机制，不依赖二次 fs/get）。
2. 365 插件钩子保留为补充（非排除 + 365 开），加 jpg 已存在则跳过。
3. ffmpeg 抽帧：**用户明确设计 = `ffmpeg-enable` 为总开关，`exclude-365-paths` 为目录范围**。故条件严格为 `FFmpegEnable && isExcluded`，**不可加 `|| !Enable365`**（那会让 365 关闭时 ffmpeg 全局生效，违背"exclude 控制抽帧目录"）。

**用户设计意图（2026-10-19 澄清）**：strm 生成后，`ffmpeg-enable` 控制是否抽帧，`exclude-365-paths` 控制"需要抽帧的目录"（即这些目录 365 处理不了，用 ffmpeg 兜底）；其余目录由 365 插件/列表 Thumb 处理。
- 排除路径：仅 ffmpeg（不依赖远程 365 缩略图，因本地/局域网直链 365 无法生成）。
- 非排除路径：列表 Thumb 内联下载（主）+ 365 插件（辅）。

**教训**：用户当场指出"你再乱修复吧"是对的——第一轮只调了门控在猜。正确做法是顺着缩略图链路读透（列表 Thumb 字段 → 365 插件依赖 fs/get → 路径匹配），定位到被删的主链路。

**提交推送**：commit `0f5e9fe`，已推 `origin/dev`（`18243b0..0f5e9fe`，synchronizer.go +46/-19）。子模块 pelagica 仍对齐 646a5dd4，无偏移。

## 缩略图仍不生成 —— 加诊断日志定位（2026-10-19 晚）
**用户反馈**：重建重启后「日志没有 ffmpeg 相关的，目录也只生成了 strm 没有图片」。

**关键排查**：
- `ExtractVideoCover` 自身不打日志；调用方（`synchronizer.go` ffmpeg 分支）原本 `err != nil 就 return`，**静默吞错**。故"无 ffmpeg 日志"无法区分「2.3 分支没执行」还是「执行了但失败被吞」。
- **配置层级陷阱（重点）**：`Openlist.Exclude365Paths` 的 yaml 是 `exclude-365-paths`，位于 **openlist 顶层**（与 `token`/`host`/`365-enable` 同级）；而 `LocalTreeGen.FFmpegEnable` 的 yaml 是 `ffmpeg-enable`，位于 **openlist.local-tree-gen 之下**。两者层级不同，配错会被**静默忽略** → `isExcluded` 恒 false → 2.3 永不执行 → 排除目录无图。这是最可能的症状成因。
- `IsExclude365Path` 用 `strings.HasPrefix(p, root)`，`p = task.Path`（带前导 `/` 的 openlist 路径，如 `/Movies/x.strm`）。排除项必须是其前缀且**带前导 `/`**（写成 `Movies` 不生效）。
- `getRealDownloadUrl(task)`：构造 openlist `/d/` 路径 (`sw.OpenlistPath`) 并跟随 302 返回终态 URL。对 **strm 文件**它解析的是 strm 本身而非其中的真实视频，ffmpeg 去抽帧可能失败（另一可能成因）。

**提交诊断日志**：commit `1fa40ee` 已推 `origin/dev`（`0f5e9fe..1fa40ee`，synchronizer.go +27/-17）。用户拉取重建后回报：仅有 `[SUCCESS] ffmpeg 环境检测通过` 与 `同步完成 总数:65 新增:0`，**完全没有任何 `[thumb-debug]` 日志**。

**真因（二次，决定性）**：缩略图块原挂在 `handleFile` 的 `writer.Write` **之后**；而 `handleFile` 在本地 strm 已存在且未变更时第 271 行**早退**（`if stat.ModTime().After(task.Modified) { return nil }`）。用户每次同步都是 `新增:0`（strm 早已生成），故全部早退、缩略图块一次都没进 —— 这同时解释了"合并后不能生成缩略图"和"无任何 ffmpeg 日志"。根因是**缩略图生成被耦合在"文件被写入"路径上，重跑同步不补图**。

**修复（synchronizer.go，BUILD/VET/GOFMT 通过，未提交）**：把缩略图逻辑抽成 `handleSyncTasks` 内的闭包 `tryGenerateThumbnail(task, localAbsPath)`，在 (a) 文件已存在早退前 与 (b) 文件新写入后 **两处调用**。这样无论 strm 是新建还是早已存在，只要同名 jpg 缺失就补生成；`os.IsNotExist` 闸门保证已有图不重复抽帧。`tryGenerateThumbnail` 必须定义在 `handleFile` 之前（同作用域闭包，否则作用域起点在引用之后导致 undefined）。

**做法**：加 `[thumb-debug]` 临时诊断日志（每文件打印 path/excluded/ffmpeg/enable365/hasThumb；ffmpeg 分支打印抽帧开始 url、失败 err+size、成功、写文件失败）。commit `1fa40ee` 已推 `origin/dev`（`0f5e9fe..1fa40ee`，+27/-17）。

**下一步（等用户反馈）**：用户重建重启后贴 `[thumb-debug]` 日志 + openlist config 片段（token/host 打码）。判读表：
`ffmpeg=false`→配置未生效；`excluded=false`→路径没匹配；`ffmpeg=true excluded=true` 无"抽帧开始"→jpg 已存在/未扫到；"抽帧开始"后"抽帧失败"→URL 问题（strm 概率高）。
**诊断日志定位后需删除并正式提交修复。**
